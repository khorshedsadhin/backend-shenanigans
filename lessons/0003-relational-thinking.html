Lesson 03 · Roadmap step 2 of 16 · তিন বসায় শেষ

একটা Fact, এক জায়গায়

MongoDB তোমাকে শিখিয়েছে সব কিছু একটা document এর ভেতরে ঢুকিয়ে রাখতে। PostgreSQL এর পুরো নিয়মটা তার উল্টো — আর এই উল্টোটাই তোমার mission এর সবচেয়ে বড় ফাঁক।

কেন এটা এখন

তোমার mission বলে: SQL প্রায় শূন্য, আর relational thinking ground up থেকে বানাতে হবে। Roadmap এর step 4 (joins), step 7 (EXPLAIN ANALYZE) আর শেষের interview round — তিনটাই এই একটা schema পড়ে। ভুল schema কে পরে index দিয়ে ঠিক করা যায় না। তাই ORM এর আগে, Nest এর সাথে connect করার আগে, এই lesson।

তিন ভাগ। Part A শুধু পড়া আর quiz, কোনো setup নেই, ~২০ মিনিট। Part B Docker Desktop বসানো আর Postgres চালু করা, ~২৫ মিনিট (একবারই, সারা course এ কাজে লাগবে)। Part C নিজের হাতে table বানানো আর ইচ্ছা করে ভাঙা, ~৩০ মিনিট। আজ শুধু Part A করলেই যথেষ্ট।

0 · আগে মনে করো

Lesson 01 তুমি blank file থেকে আবার বানিয়েছ — ওটা আসল কাজ ছিল। শুরু করার আগে একটা জিনিস স্মৃতি থেকে বের করো। ৫ মিনিট।

স্মৃতি থেকে: default scope এর একটা Nest service কেন নিজের field এ per-user data রাখতে পারে না? উত্তরে "singleton" শব্দটা ব্যবহার করো।

Default scope মানে singleton — container app চালু হওয়ার সময় একবার object বানায়, আর সেই একটা object ই সব request সামলায়, একসাথে। তাই service এর field টা সব user share করে; এক user এর data আরেক user এর response এ চলে যায়। State process এর বাইরে — database এ — রাখলে এটা হয় না।

যদি এটা লিখতে গিয়ে আটকে যাও বা "singleton" কথাটা মুখে না আসে, তাহলে এখনই ১৫ মিনিট দিয়ে Providers আর Injection Scopes পড়ে ফেলো — lesson 01 এ যেগুলো পড়া হয়নি। Code চলা আর docs এর ভাষায় বলতে পারা দুইটা আলাদা জিনিস, আর interview টা দ্বিতীয়টা দিয়েই হয়।

Part A · ধারণা~20 min · no setup

1 · তোমার Mongo অভ্যাসটা কী ছিল

তোমার Express + Mongo project এ একটা order সম্ভবত এরকম দেখতে ছিল — সব কিছু এক জায়গায়, একবার query করলেই পুরোটা পাওয়া যায়:

// mongo — একটা order document
{
  _id: "665f...",
  user: { name: "Khorshed", email: "k@mail.com" },
  items: [
    { product: "Keyboard", price: 2500, quantity: 1 },
    { product: "Mouse",    price: 800,  quantity: 2 }
  ],
  placedAt: "2026-09-20T10:00:00Z"
}

এটা পড়তে দ্রুত, লিখতে আরাম। এখন একটা বাস্তব ঘটনা ঘটাও: user তার email বদলালো।

তার ১০,০০০ order document এ email টা copy হয়ে আছে। মানে একই সত্যি ১০,০০০ জায়গায় লেখা। এখন তোমাকে ১০,০০০ জায়গায় update করতে হবে, আর তার মাঝপথে server restart হলে কিছু document এ পুরনো email, কিছুতে নতুন। Database এর ভাষায় এটার নাম update anomaly।

পুরো relational thinking এর এক লাইনের সারমর্ম এটাই:

মূল নিয়ম

একটা fact, এক জায়গায়। User এর email একটা fact — সেটা থাকবে user এর এক জায়গায়, আর বাকি সবাই সেই জায়গাটাকে দেখাবে, copy করবে না। এই copy সরানোর কাজটার নাম normalisation।

2 · Row, column, আর type যেটা আসলেই জোর করে

Postgres এ data থাকে table এ। Table এর প্রতিটা row একটা জিনিস (একজন user, একটা order)। প্রতিটা column সেই জিনিসের একটা fact, আর প্রতিটা column এর একটা declared type আছে।

এটাই Mongo থেকে প্রথম বড় পার্থক্য। Mongo তে একটা field এ আজ string, কাল number রাখা যায় — কেউ আটকাবে না, ভুলটা ধরা পড়বে ছয় মাস পর production এ। Postgres এ column এর type একটা প্রতিশ্রুতি যেটা database নিজে পাহারা দেয়: integer column এ "hello" ঢোকানোর চেষ্টা করলে insert টাই fail করে (Data Types)।

এখনকার জন্য এই কয়টা type ই যথেষ্ট:

Typeকীসের জন্যমনে রাখার কথা
text নাম, email, যেকোনো string Postgres এ varchar(n) এর চেয়ে দ্রুত না — কারণ ছাড়া length limit দিও না।
bigint id, count integer ২১৪ কোটিতে শেষ। Id এর জন্য bigint ই নাও।
numeric(10,2) টাকা, দাম টাকার জন্য কখনো float না — 0.1 + 0.2 ঠিক হয় না।
timestamptz কখন ঘটলো সবসময় এটা, timestamp না। ওটাতে timezone তথ্য হারায়।
boolean হ্যাঁ/না true, false, আর null — তিনটা অবস্থা।

3 · দুইটা key, দুইটা আলাদা কাজ

Table গুলোকে জোড়া লাগায় key। মাত্র দুইটা ধারণা, কিন্তু পুরো schema design এই দুইটার উপরে দাঁড়ানো (Constraints)।

Primary key — যে column টা একটা row কে নাম দেয়। প্রতিটা row এর আলাদা, আর কখনো null না। Mongo র _id এর সমান, কিন্তু তুমি নিজে ঠিক করো এটা কোন column।

Foreign key — যে column টা অন্য table এর primary key এর দিকে আঙুল তোলে। আর এখানেই Postgres এর আসল ক্ষমতা: database এমন কোনো row ঢুকতেই দেয় না যার আঙুল শূন্যের দিকে। নেই এমন user এর order তৈরি করা যাবে না — application এ if লিখে না, database এ নিয়ম লিখে।

Mongo তে এই পাহারাটা নেই। তুমি userId রাখতে পারো, কিন্তু সেই user মুছে গেলে document টা একটা orphan হয়ে বসে থাকে, আর টের পাওয়া যায় যেদিন কেউ ওটা পড়তে যায়।

4 · One-to-many: আঙুল সবসময় "many" দিক থেকে ওঠে

একজন user এর অনেক order। Order টা user এর দিকে আঙুল তোলে, উল্টোটা না — কারণ "many" দিকের প্রতিটা row এর মালিক একজন, কিন্তু "one" দিকে কতজন থাকবে তার সংখ্যা আগে থেকে জানা নেই।

usersorders
id = 1 · email = k@mail.com
id = 2 · email = r@mail.com		 id = 10 · user_id = 1
id = 11 · user_id = 1
id = 12 · user_id = 2

Email টা orders এ একবারও নেই। User 1 email বদলালে একটা row বদলায়, আর তার দশ হাজার order সঙ্গে সঙ্গে নতুন email দেখায়। Section 1 এর সমস্যাটা এভাবেই শেষ হলো।

5 · Many-to-many: তৃতীয় কোনো রাস্তা নেই

একটা order এ অনেক product, আর একটা product অনেক order এ। এখন আঙুল কোন দিকে তুলবে? কোনো দিকেই না — তৃতীয় একটা table লাগবে। তার নাম join table: তার প্রতিটা row মানে "এই order এর সাথে এই product এর একটা সম্পর্ক"।

orders          order_items                 products
id=10  ◄──── order_id=10, product_id=7,  ────►  id=7  Keyboard
              quantity=1
id=10  ◄──── order_id=10, product_id=9,  ────►  id=9  Mouse
              quantity=2

খেয়াল করো quantity কোথায় বসেছে। ওটা product এর fact না (Mouse এর নিজের কোনো quantity নেই), order এর fact ও না (order এর প্রতিটা product এর আলাদা quantity)। ওটা সম্পর্কটার fact — তাই ওটার জায়গা join table এ। এটা ধরতে পারলে many-to-many তোমার হয়ে গেছে।

Mongo র অভ্যাস এখানে টানবে — "একটা array column এ product গুলো রেখে দিই"। Postgres এ array type আছে, কিন্তু এই কাজে ওটা ভুল: array এর ভেতরের value তে foreign key খাটে না, মানে নেই এমন product order এ ঢুকে যেতে পারবে। Array হলো Mongo অভ্যাসের ছদ্মবেশ।

6 · কী পেলাম, কী দিলাম

Mongo: এক document

{ user: { email }, items: [...] }

// পড়া: এক query, দ্রুত
// email বদল: ১০,০০০ জায়গায়
// ভুল data: কেউ আটকায় না

Postgres: চারটা table

users · orders · order_items · products

// পড়া: join লাগে
// email বদল: ১ জায়গায়
// ভুল data: database refuse করে

দাম দিতে হচ্ছে join — পড়ার সময় টেবিল জোড়া লাগানোর কাজ। সেটা roadmap এর step 4, আর সেটা যখন ধীর হয় তখন step 7 এর index। কিন্তু ভুল schema কে index দিয়ে ঠিক করা যায় না — duplicate data থেকে জন্মানো bug কোনো index দূর করে না। এজন্যই schema আগে।

8 · মনে করে লেখো

নিচের Mongo document টা relational এ ভাঙো — শুধু table এর নাম আর প্রতিটার key গুলো লেখো (column এর পুরো list দরকার নেই)।
{ _id, title, author: { name, email }, comments: [ { userId, text } ], tags: [ "nest", "sql" ] }

users — PK id। Author আর comment এর লেখক দুইজনেই user, তাই একটাই table।
posts — PK id, FK author_id → users(id)। Author এর name/email এখানে copy হবে না।
comments — PK id, FK post_id → posts, FK user_id → users। One-to-many, তাই আঙুল comment এর দিক থেকেই উঠছে।
tags — PK id, আর তার সাথে join table post_tags (post_id, tag_id, PK দুইটা মিলে)। একটা tag অনেক post এ, একটা post এ অনেক tag — many-to-many।

tags এর জন্য join table টা যদি মিস করো, সেটাই সবচেয়ে common ভুল: string এর array দেখলে মনে হয় ওটা ছোট জিনিস, কিন্তু "একটা tag এ কত post" প্রশ্নটা তখন উত্তরহীন হয়ে যায়।

Part B · Postgres চালু করা~25 min · একবারই

এই কাজটা সারা course এ একবারই করতে হবে, আর step 5, 6, 7, 11, 12, 15 — সবগুলোতে এই Postgres টাই লাগবে। তোমার machine এ এখন Docker নেই, তাই শুরু ওখান থেকেই।

  1. Docker Desktop বসাও — docs.docker.com এর Windows install page থেকে। WSL 2 backend টাই নাও (default)। একবার restart লাগতে পারে। শেষে PowerShell খুলে docker --version চালাও; version দেখালে হয়ে গেছে।
  2. Postgres container চালাও। এক লাইন, PowerShell এ: 
    docker run --name scale-pg -e POSTGRES_PASSWORD=devpass `
  -e POSTGRES_DB=scalelab -p 5432:5432 `
  -v scale-pg-data:/var/lib/postgresql/data -d postgres:17
    -v অংশটা সবচেয়ে জরুরি: এটা একটা named volume, container মুছে ফেললেও তোমার data থাকবে। Image এর option গুলো Docker Hub এর postgres page এ।
  3. ভেতরে ঢোকো — docker exec -it scale-pg psql -U postgres -d scalelab। Prompt scalelab=# হলে তুমি psql এর ভেতরে, আর এখন যা লিখবে সব SQL। select version(); চালাও (semicolon না দিলে কিছুই হবে না — এটা সবার প্রথম দিনের ভুল)।
  4. বেরোতে \q। পরে আবার একই docker exec command। Container বন্ধ থাকলে docker start scale-pg।
Part B শেষ। select version(); এর output টা তুমি দেখেছ মানে তোমার নিজের database চলছে। বিশ্রাম নাও — Part C আলাদা বসা।
Part C · হাতে-কলমে schema~30 min · psql

Section 1–5 এর ধারণাগুলো এখন নিজের হাতে টাইপ করবে। Copy-paste করো না — টাইপ করার সময় যে ভুল হবে, সেই ভুলগুলোই শেখায়। Syntax এর জন্য Constraints page পাশে খোলা রাখো, আমাকে না।

  1. users বানাও: id primary key, email text not null unique, name text not null, created_at timestamptz not null default now()। Id এর জন্য bigint generated always as identity লেখো — এটাই Postgres এর auto-increment।
  2. products: id primary key, name text not null, price numeric(10,2) not null।
  3. orders: id primary key, user_id bigint not null references users(id), placed_at timestamptz not null default now()। এই references এক শব্দটাই section 3 এর পুরো পাহারা।
  4. order_items — join table: order_id bigint not null references orders(id), product_id bigint not null references products(id), quantity integer not null check (quantity > 0), আর শেষে primary key (order_id, product_id)। দুইটা column মিলে একটা primary key — মানে একই product একই order এ দুইবার row হতে পারবে না।
  5. \dt দিয়ে চারটা table দেখো, \d orders দিয়ে orders এর constraint গুলো দেখো। Foreign key এর নাম Postgres নিজে দিয়েছে — নামটা খেয়াল করো, error message এ ওটাই আসবে।
  6. একজন user, একটা product, তার একটা order, আর order_items এ একটা row — insert করে ফেলো। User এর id জানতে select id, email from users;।

এখন ইচ্ছা করে ভাঙো — চারবার

Lesson 01 এ ভাঙার কাজটাই সবচেয়ে কাজে দিয়েছিল। প্রতিবার error পড়ার আগে জোরে জোরে বলো কোন constraint টা আটকালো, তারপর message এ মিলিয়ে দেখো।

  1. নেই এমন user এর order: insert into orders (user_id) values (9999);
  2. একই email দুইবার: প্রথম user এর email দিয়েই আবার একটা user insert করো।
  3. quantity শূন্য দিয়ে একটা order_items row insert করো।
  4. যে user এর order আছে তাকে মুছে ফেলার চেষ্টা করো: delete from users where id = 1; — আঙুল এখনো তার দিকে তোলা, তাই Postgres না বলবে। এটা কীভাবে ঠিক করে সেটা পরের কথা, এখন শুধু দেখো।

চারটা error মোটামুটি এরকম দেখাবে (তোমার version এ শব্দ একটু আলাদা হতে পারে):

1. ERROR:  insert or update on table "orders" violates foreign key
        constraint "orders_user_id_fkey"
2. ERROR:  duplicate key value violates unique constraint "users_email_key"
3. ERROR:  new row for relation "order_items" violates check constraint
        "order_items_quantity_check"
4. ERROR:  update or delete on table "users" violates foreign key
        constraint "orders_user_id_fkey" on table "orders"

চারটাতেই একই গঠন: কোন table, কোন নিয়ম ভাঙলো, নিয়মটার নাম কী। Postgres এর error message পড়তে শেখা মানে অর্ধেক debugging শেখা।

শেষ ধাপ — মুছে আবার বানাও

Lesson 01 এ তুমি নিজেই এটা করেছিলে, আর সেটাই তোমাকে পাস করিয়েছে। এখানেও করো: drop table order_items, orders, products, users; — তারপর lesson না দেখে চারটা table আবার লেখো। দ্বিতীয়বারে যেখানে আটকাবে, ওটাই তোমার আসল ফাঁক। drop এর order টাও ভাবো: আঙুল তোলা table আগে মুছতে হয়, না হলে Postgres আবার না বলবে।

Part C শেষ হলে terminal এ আমাকে বলো: চারটা error এর ভেতরে কোনটা তুমি আগে থেকে ঠিক বলতে পেরেছিলে, আর blank থেকে আবার লেখার সময় কোথায় আটকেছিলে। ওটা দিয়েই পরের lesson ঠিক হবে — joins নাকি আরেক ধাপ schema design।
