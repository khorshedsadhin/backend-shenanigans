Lesson 01 · Roadmap step 1 of 16 · দুই বসায় শেষ

The Container

NestJS কেন তোমাকে নিজে new দিয়ে service বানাতে দেয় না — আর এই "না" টাই কেন তোমার backend কে scale করার প্রথম ধাপ।

কেন এটা আগে

তোমার mission: backend engineer হিসেবে চাকরি পাওয়া। প্রায় সব NestJS interview শুরু হয় এই প্রশ্ন দিয়ে: "Express না নিয়ে Nest কেন?" আর প্রথম মাসে তুমি যত bug পাবে, তার বেশিরভাগ হবে wiring bug। দুটোর উত্তর একই — আর সেটাই এই lesson।

এই lesson দুই ভাগে। Part A শুধু পড়া আর quiz, কোনো setup নেই, ~১৫ মিনিট। Part B হাতে-কলমে, ~২৫ মিনিট — weekend এর জন্য রাখতে পারো। আজ শুধু Part A করলেই যথেষ্ট।

Part A · ধারণা~15 min · no setup

1 · Express এ তুমি নিজেই wiring করো

তোমার Express project এ কোথাও এরকম একটা file ছিল:

// express — wiring তুমি নিজে করছ
const db = require('./db');
const userService = new UserService(db);
const userRouter  = new UserRouter(userService);

এটা কাজ করে। কিন্তু project বড় হলে তিনটা সমস্যা আসে:

  1. যে file এর UserService লাগবে, তাকেই জানতে হবে কীভাবে এটা বানাতে হয়। Constructor বদলালে সব জায়গায় বদলাতে হয়।
  2. Test এ আসল database এর জায়গায় fake দিতে চাইলে প্রতিটা test file এ আবার হাতে wiring।
  3. দুইটা file যদি আলাদা করে new UserService(...) করে, তাহলে দুইটা instance — দুইটা আলাদা cache, দুইটা আলাদা connection pool। একই জিনিসের দুইটা "সত্য"।

2 · Nest এর উত্তর: বানিও না, শুধু বলো কী লাগবে

NestJS এর ভেতরে একটা IoC container আছে — inversion of control। তুমি আর নিজে object বানাও না। তুমি শুধু declare করো কোন class এর কী লাগবে। App চালু হওয়ার সময় Nest একবারে সব বানিয়ে জোড়া লাগিয়ে রাখে।

তুমি লেখো

@Injectable()
export class UserService {
  constructor(
    private readonly db: Database,
  ) {}
}

Nest নিজে করে

// app startup এ,
// একবারই, ঠিক order এ:
const db = new Database();
const userService =
  new UserService(db);

তুমি কখনো new UserService লেখো না। Constructor এ লিখে দাও কী লাগবে, container সেটা দিয়ে দেয়। Object বানানোর control আর তোমার হাতে নেই — এটাই "IoC" এর মানে (official docs)।

তিনটা decorator যারা আসল কাজ করে

Decorator তোমার কাছে নতুন, তাই আগে এটা পরিষ্কার করি। Decorator হলো @ দিয়ে শুরু একটা function, যেটা class এর গায়ে কিছু লুকানো তথ্য (metadata) লাগিয়ে দেয়। Class কী করে সেটা বদলায় না। Framework class সম্পর্কে কী জানে, সেটা বদলায়।

  • @Injectable() — "এই class container চালাতে পারবে।" Constructor এ কী কী parameter আছে সেই তথ্য লাগিয়ে দেয়। এটা না থাকলে Nest দেখতেই পায় না constructor কী চায়।
  • @Controller('users') — "এই class HTTP request ধরে।" একটা URL prefix এর মালিক, আর তার method গুলোতে route লেখা থাকে। তোমার Express router, উল্টো দিক থেকে।
  • @Module({...}) — "এটা একটা সীমানা, আর এর ভেতরে এরা থাকে।" এটাতেই সবাই আটকায়, তাই এর জন্য আলাদা section।
এখানে সাবধান

@Injectable() class কে শুধু injectable বানায়। এটা register করে না। Register করা আলাদা একটা কাজ — module এর providers array তে class টা লেখা। এই দ্বিতীয় ধাপ ভুলে যাওয়াই beginner দের সবচেয়ে common NestJS error। নিচের quiz এ এটা দেখবে।

3 · Module মানে সীমানা, folder না

একটা module এ চারটা array, প্রতিটা আলাদা প্রশ্নের উত্তর দেয়:

@Module({
  imports:     [DatabaseModule],  // অন্য module থেকে আমার কী লাগবে
  controllers: [UserController],  // আমার HTTP দরজা
  providers:   [UserService],     // আমার নিজের জিনিস, ভেতরে inject হয়
  exports:     [UserService],     // যে আমাকে import করে, তাকে ধার দিই
})
export class UserModule {}

সবচেয়ে জরুরি নিয়ম: provider তার module এর private, যতক্ষণ না সেটা export করা হয়। UserService কে providers এ রাখলে সেটা শুধু ওই একই module এর UserController আর অন্য provider রা পায় — আর কেউ না।

OrderModule যদি UserService চায়, তাহলে দুইটা জিনিসই লাগবে: UserModule কে সেটা export করতে হবে, আর OrderModule কে UserModule import করতে হবে। একটা দিলে হবে না।

এটা শুধু folder সাজানো না — app চালু হওয়ার সময় Nest এটা আসলেই চেক করে। এজন্য বড় Nest codebase পরিষ্কার থাকে, আর বড় Express codebase import এর জালে পেঁচিয়ে যায়।

4 · Scale এর লাভ: singleton আর stateless

By default, container প্রতিটা provider এর পুরো app এর জন্য একটাই instance বানায়। Nest docs পরিষ্কার বলে: "A single instance of the provider is shared across the entire application. The instance lifetime is tied directly to the application lifecycle." (Injection Scopes)

একটা instance। সব request সামলায়। একই সময়ে। তাই একটা নিয়ম মানতেই হয় — আর পুরো roadmap এর বাকি সব কিছু এই নিয়মের উপর দাঁড়িয়ে:

Scale এ ভাঙবে

@Injectable()
export class CartService {
  // সব user এর জন্য একটাই, সারাজীবন
  private items = [];

  add(item) { this.items.push(item); }
}

Scale এ ঠিক থাকবে

@Injectable()
export class CartService {
  constructor(private db: Database) {}

  // state process এর বাইরে থাকে
  add(userId, item) {
    return this.db.insert(userId, item);
  }
}

বাম দিকের code এ এক user এর cart আরেক user এর cart এ ঢুকে যায় — আর সেটা হয় শুধু একসাথে অনেক request এলে। তুমি নিজে একটা একটা করে test করলে ঠিকই দেখাবে, production এ গিয়ে ভাঙবে। ডান দিকের code process এর memory তে কোনো per-request state রাখে না।

এটা কোথায় যাচ্ছে

মনে রাখো: যে service memory তে state রাখে না, সেটা stateless service। Stateless হলেই তুমি app এর দশটা copy একটা load balancer এর পেছনে চালাতে পারো, কারণ যেকোনো copy যেকোনো request এর উত্তর দিতে পারে। Roadmap এর step 12–15 — caching, queue, horizontal scaling — সব ধরে নেয় যে step 1 এ তুমি এটা ঠিক করেছ। পুরো course এর সুতা এটাই।

5 · নিজেকে চেক করো

উপরে scroll না করে উত্তর দাও। এখানে ভুল করা, চিনে চিনে ঠিক করার চেয়ে বেশি কাজের।

Check 1

App চালু হতেই crash: Nest can't resolve dependencies of the UserController (?). Please make sure that the argument UserService at index [0] is available in the UserModule context. তুমি UserService এ @Injectable() দিয়েছ। কী বাকি আছে?

Check 2

OrderModule এর UserService লাগবে, যেটা UserModule এর providers এ আছে। সবচেয়ে ছোট সঠিক change কোনটা?

Check 3

Default scope এর একটা service এর private field এ তুমি per-user একটা value রাখলে। Local এ পুরোপুরি ঠিক চলে। Production এ এটা bug কেন?

6 · মনে করে লেখো

মাথায় lesson টা বন্ধ করো। স্মৃতি থেকে লেখাই কোনো কিছুকে চেনা থেকে জানা তে নিয়ে যায়।

স্মৃতি থেকে: @Module এর চারটা array কী কী, আর প্রতিটা কোন প্রশ্নের উত্তর দেয়?

imports — অন্য কোন module এর export করা provider আমার লাগবে?
controllers — এখানে কোন class গুলো HTTP request ধরে?
providers — কোন class গুলো আমার নিজের, যেগুলো আমি বানাই আর ভেতরে inject করি?
exports — আমার কোন provider আমি ধার দিই, যারা আমাকে import করে তাদের?

exports বাদ পড়লে চিন্তা নেই, ওটাই সবাই ভোলে — আর ওটাই module এর সীমানা পার হওয়া "can't resolve dependencies" error এর কারণ।

Part A শেষ। আজকের জন্য এটুকুই যথেষ্ট। Part B weekend এ করো, অথবা এখনই যদি energy থাকে।
Part B · হাতে-কলমে~25 min · Node + terminal

এই অংশটাই আসলে skill বানায়। শুরু করার আগে terminal এ node --version চালিয়ে দেখো Node আছে কিনা।

  1. Project বানাও: npm i -g @nestjs/cli, তারপর nest new scale-lab। এই scale-lab project টা পরের lesson এও লাগবে, মুছে ফেলো না।
  2. একটা feature module বানাও: nest g module users, nest g controller users, nest g service users। users.module.ts খুলে চারটা array খোঁজো। CLI কী নিজে register করেছে, আর কী করেনি — খেয়াল করো।
  3. UsersService এ একটা findAll() লেখো যেটা hardcoded array return করে। Service টা controller এ inject করো, আর একটা @Get() handler থেকে return করো। npm run start:dev চালিয়ে browser এ http://localhost:3000/users খোলো।
  4. ইচ্ছা করে ভাঙো। providers array থেকে UsersService মুছে restart দাও। Error টা মন দিয়ে পড়ো — এখন তুমি জানো এর মানে কী। তারপর ফেরত বসাও।
  5. সীমানা পার করে ভাঙো। nest g module orders আর nest g service orders। OrdersService এ UsersService inject করো। Fail করবে। exports + imports দিয়ে ঠিক করো যতক্ষণ না চালু হয়।
  6. Singleton প্রমাণ করো। UsersService এর constructor এ console.log('constructed') দাও। Restart দিয়ে endpoint টা পাঁচবার hit করো। কয়টা log line এলো গুনে দেখো, আর পড়ার আগে জোরে জোরে বলো কেন এই সংখ্যা।
Part B শেষ হলে terminal এ আমাকে বলো: কয়টা log line এলো আর কেন, আর step 5 এ কী ঠিক করলে। এটা দিয়েই পরের lesson ঠিক হবে।
