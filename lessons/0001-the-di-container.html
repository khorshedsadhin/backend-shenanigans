The Container

Why NestJS refuses to let you new your own services — and why that refusal is the first thing that makes your backend scalable.

Why this, first

Your mission is to be hired as a backend engineer. Every NestJS interview opens with some version of "why Nest instead of Express?" — and almost every bug you will hit in your first month is a wiring bug. Both have the same answer, and it is the topic of this lesson.

1 · The problem Express leaves you with

In the Express project you built, you wired dependencies by hand. Somewhere there was a file that did roughly this:

// express — you are the wiring
const db = require('./db');
const userService = new UserService(db);
const userRouter  = new UserRouter(userService);

This works. It also quietly creates three problems that only appear at scale. Every file that needs UserService must know how to build one, so the constructor signature leaks across your whole codebase. Swapping the real database for a fake one in a test means re-doing that wiring by hand in every test file. And nothing stops two different files from each calling new UserService(...), so you can end up with two instances holding two different caches, two different connection pools, two different truths.

2 · Nest's answer: declare, don't construct

NestJS ships an IoC container — inversion of control. You stop constructing dependencies and start declaring them. The framework builds the object graph for you, once, at startup.

You write this

@Injectable()
export class UserService {
  constructor(
    private readonly db: Database,
  ) {}
}

Nest does this

// at application startup,
// exactly once, in order:
const db = new Database();
const userService =
  new UserService(db);

You never call new UserService. You describe what it needs, and the container satisfies it. That inversion — you no longer control construction — is what the "IoC" in the official docs stands for.

The three decorators doing the work

Decorators are new to you, so be precise about what one is. A decorator is a function prefixed with @ that attaches hidden metadata to a class. It does not change what the class does. It changes what the framework knows about it.

  • @Injectable() — "this class may be managed by the container." It attaches type metadata about the constructor parameters. Without it, Nest cannot see what the constructor wants.
  • @Controller('users') — "this class handles HTTP." It is a class that owns a URL prefix, with the routing table declared on its methods. This is your Express router, inverted.
  • @Module({...}) — "here is a boundary, and here is what lives inside it." This is the one that trips people up, so it gets its own section.
Precision matters here

@Injectable() makes a class injectable. It does not register it. Registration is a separate, explicit act — putting the class in a module's providers array. Forgetting the second step is the single most common NestJS error a beginner hits, and you will see it in the quiz below.

3 · Modules are boundaries, not folders

A module has four arrays, and each answers a different question:

@Module({
  imports:     [DatabaseModule],  // what I need from elsewhere
  controllers: [UserController],  // my HTTP entry points
  providers:   [UserService],     // what I own and inject internally
  exports:     [UserService],     // what I lend to modules importing me
})
export class UserModule {}

The rule that carries all the weight: a provider is private to its module unless it is exported. Listing UserService in providers makes it available to UserController and to other providers in that same module — nowhere else. For OrderModule to inject UserService, two things must both be true: UserModule must export it, and OrderModule must import UserModule.

This is a real encapsulation boundary, enforced at startup — not a folder convention. It is why a large Nest codebase stays navigable where a large Express codebase turns into a web of mutual imports.

4 · The scaling payoff: singletons and statelessness

By default, the container creates one instance of each provider for the entire application lifetime. The Nest docs are unambiguous: "A single instance of the provider is shared across the entire application. The instance lifetime is tied directly to the application lifecycle." (Injection Scopes)

One instance. Serving every request. Concurrently. Which forces a discipline that turns out to be the foundation of everything else on your roadmap:

Broken at scale

@Injectable()
export class CartService {
  // shared by ALL users, forever
  private items = [];

  add(item) { this.items.push(item); }
}

Correct at scale

@Injectable()
export class CartService {
  constructor(private db: Database) {}

  // state lives outside the process
  add(userId, item) {
    return this.db.insert(userId, item);
  }
}

The left version leaks one user's cart into another's, and it does so only under concurrency — which is why it passes your manual testing and fails in production. The right version keeps no per-request state in the process.

Where this goes

Hold onto this: a service that keeps no state in memory is a stateless service. Stateless services are the precondition for running ten copies of your app behind a load balancer, because any copy can answer any request. Everything in roadmap steps 12–15 — caching, queues, horizontal scaling — assumes you got this right in step 1. This is the thread running through the whole course.

5 · Check yourself

Answer before scrolling back. Getting one wrong here is worth more than getting it right by recognition.

Check 1

Your app crashes at boot: Nest can't resolve dependencies of the UserController (?). Please make sure that the argument UserService at index [0] is available in the UserModule context. You have already added @Injectable() to UserService. What is missing?

Check 2

OrderModule needs to inject UserService, which is declared in UserModule's providers. What is the minimum correct change?

Check 3

You store a per-user value on a private field of a default-scoped service. It works perfectly in local testing. Why is it a production bug?

6 · Retrieve it

Close the lesson in your head first. Writing it from memory is what moves this from recognised to known.

From memory: what are the four arrays of @Module, and what question does each one answer?

imports — which other modules' exported providers do I need?
controllers — which classes in here handle incoming HTTP requests?
providers — which classes do I own, build, and inject internally?
exports — which of my providers do I lend to modules that import me?

If you missed exports, that is the usual one — and it is the one that causes the "can't resolve dependencies" error across module boundaries.

7 · Do it for real

Twenty minutes at the keyboard. This is the part that actually builds the skill.

  1. Scaffold a project: npm i -g @nestjs/cli, then nest new scale-lab.
  2. Generate a feature module: nest g module users, nest g controller users, nest g service users. Open users.module.ts and find the four arrays. Notice what the CLI registered for you, and what it did not.
  3. Give UsersService a findAll() that returns a hardcoded array. Inject the service into the controller and return it from a @Get() handler. Run npm run start:dev and hit http://localhost:3000/users.
  4. Break it deliberately. Delete UsersService from the providers array and restart. Read the error closely — you now know exactly what it means. Put it back.
  5. Break it across a boundary. nest g module orders and nest g service orders. Inject UsersService into OrdersService. It will fail. Fix it with exports + imports until it boots.
  6. Prove the singleton. Add console.log('constructed') to UsersService's constructor. Restart, then hit the endpoint five times. Count the log lines, and explain the number out loud before you read on.
