Incident 01 · Roadmap step 1 এর পরে · দুই বসায় শেষ

CPU 12%, তবু API slow

Server দেখতে ঠিকঠাক, কিন্তু user রা অপেক্ষা করছে। সময় যাচ্ছে কোথায় — আর কীভাবে guess না করে খুঁজে বের করবে।

কেন এটা

তোমার mission এর একটা লাইন: whiteboard এ বোঝাতে পারা কেন একটা request slow, আর {index, cache, queue, replica, আরো app instance} এর মধ্যে কোনটা সঠিক fix — আর বাকি চারটা কেন না। প্রতিটা Incident lesson এই দক্ষতার একটা টুকরা। আজকেরটা সবচেয়ে মৌলিক: সময়টা কি কাজে যাচ্ছে, নাকি অপেক্ষায়?

আগে যা লাগবে: Lesson 01। Part A যেকোনো সময় পড়া যায়। Part B তে Lesson 01 এর scale-lab project লাগবে।

Part A · ঘটনা আর চিন্তার ধরন~20 min · no setup

1 · ঘটনা

রাত ১০টা। Monitoring dashboard এ দেখা যাচ্ছে:

CPU (total)      12%
Memory           41%
Error rate       0.1%
p95 latency      3.1 s    ← সাধারণত 120 ms

p95 latency মানে: ১০০ টা request এর মধ্যে ৯৫ টা এর চেয়ে দ্রুত শেষ হয়েছে। অর্থাৎ অনেক user ৩ সেকেন্ডের বেশি অপেক্ষা করছে। Team lead জিজ্ঞেস করলেন: "CPU তো প্রায় খালি। Server ঠিক আছে। তাহলে slow কেন?"

তুমি কী দেখবে, কোন order এ? পড়ার আগে মনে মনে একটা উত্তর ঠিক করো।

2 · Request এর সময় = কাজ + অপেক্ষা

একটা request এর মোট সময় দুই ভাগে যায়:

  • কাজ (CPU): তোমার code আসলে হিসাব করছে — loop, JSON বানানো, hash করা।
  • অপেক্ষা (waiting): code কিছু করছে না, অন্য কারো উত্তরের জন্য বসে আছে — database, অন্য একটা API, pool এ খালি connection, একটা lock।

CPU graph শুধু প্রথম ভাগ মাপে। অপেক্ষা CPU তে দেখাই যায় না। একটা দোকানের কথা ভাবো: দোকানদার বসে আছে কারণ supplier এর মাল এখনো আসেনি। দোকানদার busy না (CPU কম), কিন্তু customer এর লাইন বাড়ছে (latency বেশি)।

তাই "CPU কম কিন্তু slow" এর দুইটা সম্ভাব্য ব্যাখ্যা আছে। দুইটাই দেখতে হবে।

3 · ফাঁদ ১: ১২% মানে "একটা core পুরো ভরা" হতে পারে

Server এ ৮টা core থাকলে, total CPU হলো ৮টার গড়। একটা core ১০০% আর বাকি সাতটা ০% হলে total দেখায় ১০০ ÷ ৮ = ১২.৫%। দেখতে "প্রায় খালি", আসলে একটা core দম বন্ধ করে দৌড়াচ্ছে।

Node এর ক্ষেত্রে এটা খুব জরুরি, কারণ তোমার JavaScript একটাই thread এ চলে। Node docs: "Node.js runs JavaScript code in the Event Loop", আর "While a thread is blocked working on behalf of one client, it cannot handle requests from any other clients." (Don't Block the Event Loop)

মানে: একটা request যদি ৩ সেকেন্ড ধরে CPU তে ভারী কাজ করে (বড় loop, বিশাল JSON parse, sync crypto), তাহলে ওই ৩ সেকেন্ড অন্য সব user আটকে থাকে — যদিও total CPU মাত্র ১২%।

কীভাবে চেক করবে

Total না, প্রতিটা core আলাদা দেখো। Windows এ: Task Manager → Performance → CPU → graph এ right-click → Change graph to → Logical processors। একটা box ভরা আর বাকিগুলো খালি? তাহলে event loop block। Linux server এ একই কাজ করে htop।

4 · ফাঁদ ২: আসলেই অপেক্ষা

যদি সব core ই কম থাকে, তাহলে code আসলেই কারো জন্য বসে আছে। সবচেয়ে common জায়গাগুলো:

  • Slow query. Database একটা query তে ২.৮ সেকেন্ড নিচ্ছে, কারণ পুরো table পড়ছে। Fix সাধারণত index — roadmap step 7।
  • Connection pool ভরা। App database এর সাথে অল্প কয়টা connection খোলা রাখে, আর সেগুলো share করে। Postgres এর Node driver এ default হলো ১০টা। সব busy হলে "requests will wait in a FIFO queue until a client becomes available", আর default এ এই অপেক্ষার কোনো timeout নেই (node-postgres Pool)। প্রতিটা query দ্রুত, তবু request লাইনে দাঁড়িয়ে slow — roadmap step 15।
  • বাইরের API, timeout ছাড়া। Payment বা SMS provider slow হলে তোমার request ও ঠিক ততটাই slow। Timeout না দিলে চিরকাল অপেক্ষা করতে পারে।
  • Lock. দুইটা transaction একই row চাইছে, একটা আরেকটার জন্য অপেক্ষা করছে — roadmap step 6।

একটা নাম মনে রাখো: saturation। Brendan Gregg এর USE Method বলে: "For every resource, check utilization, saturation, and errors." Saturation মানে একটা resource এর কাছে এমন কাজ জমে আছে যেটা সে এখনো ধরতে পারছে না — সাধারণত একটা queue। CPU এর utilization কম, কিন্তু connection pool saturated — এটাই ফাঁদ ২।

কেন "আরো server দাও" সবসময় fix না

Event loop block হলে আরো app instance (step 14) আসলেই সাহায্য করে — কাজ ভাগ হয়ে যায়। কিন্তু slow query হলে আরো instance মানে একই database এ আরো বেশি চাপ। সমস্যা বাড়ে। কোথায় অপেক্ষা হচ্ছে না জেনে fix বেছে নিলে ভুল fix এর সম্ভাবনাই বেশি।

5 · Triage: তিন ধাপ, এই order এ

  1. প্রতিটা core দেখো। একটা ভরা? → event loop এ ভারী কাজ। সব খালি? → অপেক্ষা, ধাপ ২ এ যাও।
  2. প্রতিটা ধাপের সময় মাপো, guess করো না। Slow endpoint এর প্রতিটা await এর আগে-পরে সময় log করো: 
    const t = Date.now();
const orders = await this.db.query(...);
console.log('db query', Date.now() - t, 'ms');
    Step 9 এ এটা ঠিকমতো logging দিয়ে করব। আপাতত এটাই যথেষ্ট।
  3. সবচেয়ে বড় সংখ্যাটাই fix বলে দেয়। Query নিজে slow → index। Query দ্রুত কিন্তু শুরু হতে দেরি → pool। বাইরের call slow → timeout, বা কাজটা queue তে পাঠাও (step 13)।

6 · নিজেকে চেক করো

Check 1

৮ core এর server। Total CPU ১২%। Per-core graph এ একটা core ১০০%, বাকি সাতটা প্রায় ০%। সবচেয়ে সম্ভাব্য কারণ কী?

Check 2

সব core কম। /orders ৩ সেকেন্ড নেয়। তোমার timing log বলছে এর মধ্যে ২.৮ সেকেন্ড একটা database query তে যাচ্ছে। প্রথম fix কোনটা?

Check 3

সব core কম। প্রতিটা query একা চালালে ২০ ms। কিন্তু traffic বাড়লে request গুলো কয়েক সেকেন্ড নেয়। App এর connection pool এ max ১০টা connection। কী হচ্ছে?

7 · মনে করে লেখো

স্মৃতি থেকে: "CPU কম কিন্তু API slow" — কোন তিনটা জিনিস দেখবে, কোন order এ, আর কেন ওই order?

১. প্রতিটা core আলাদা। Total CPU একটা ভরা core লুকিয়ে ফেলতে পারে। একটা ভরা = event loop এ ভারী কাজ।
২. প্রতিটা ধাপের সময়। সব core খালি হলে code অপেক্ষা করছে — কোথায়, সেটা মেপে বের করো।
৩. সবচেয়ে বড় সংখ্যা → fix। Slow query → index। Pool এ লাইন → pooling। বাইরের API → timeout বা queue।

Order টা এমন কারণ প্রথম ধাপ সবচেয়ে সস্তা (এক নজর), আর সেটাই ঠিক করে দেয় তুমি "কাজ" খুঁজবে নাকি "অপেক্ষা"।

Part A শেষ। Part B তে তুমি নিজের চোখে দুইটা ফাঁদই বানাবে আর মাপবে।
Part B · নিজে বানাও, নিজে মাপো~15 min · scale-lab
  1. scale-lab এর UsersController এ দুইটা route যোগ করো (কোনো @Get(':id') থাকলে তার উপরে রাখো): 
    @Get('slow-wait')
async slowWait() {
  // database বা বাইরের API এর অপেক্ষার নকল
  await new Promise((r) => setTimeout(r, 3000));
  return 'waited';
}

@Get('slow-cpu')
slowCpu() {
  // ৩ সেকেন্ড ধরে শুধু CPU পোড়ায়
  const end = Date.now() + 3000;
  while (Date.now() < end) {}
  return 'burned';
}
  2. npm run start:dev। তারপর আরেকটা PowerShell window এ একসাথে ৫টা request পাঠাও। curl.exe লিখবে, শুধু curl না — PowerShell এ curl অন্য একটা command। 
    curl.exe -s -Z --parallel-immediate -o NUL -w "%{time_total}s\n" "http://localhost:3000/users/slow-wait?n=[1-5]"
    প্রতিটা request কত সেকেন্ড নিলো, লিখে রাখো।
  3. একই command, এবার slow-cpu দিয়ে। চলার সময় Task Manager এর Logical processors view খোলা রাখো। সময়গুলো লিখে রাখো, আর কয়টা core এর graph উঠলো দেখো।
  4. slow-cpu এর ৫টা request চলার সময়ই তৃতীয় একটা window থেকে সাধারণ /users hit করো: 
    curl.exe -s -o NUL -w "%{time_total}s\n" http://localhost:3000/users
    এটা তো কোনো ভারী কাজ করে না। তবু কত সময় নিলো?
  5. জোরে জোরে ব্যাখ্যা করো: slow-wait এর ৫টা কেন প্রায় একই সময়ে শেষ হলো, আর slow-cpu এর ৫টা কেন হলো না? /users কেন আটকে গেল?
