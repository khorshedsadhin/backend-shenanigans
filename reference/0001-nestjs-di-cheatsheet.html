NestJS DI & Modules

The wiring rules, the decorators, and the error messages — on one page.

The four module arrays

ArrayAnswersGotcha
imports Which other modules do I need? Takes modules, never providers.
controllers Which classes handle HTTP here? Controllers are never put in providers, and are never exported.
providers What do I own and inject internally? Registration happens here — @Injectable() alone does nothing.
exports What do I lend to modules that import me? Must also appear in providers. Omitting this is the #1 cross-module bug.
The one rule

A provider is private to its module unless exported. Sharing needs both halves: the owner exports it, the consumer imports the owning module.

Canonical shapes

Service (provider)

import { Injectable } from '@nestjs/common';

@Injectable()
export class UsersService {
  constructor(
    private readonly db: Database,
  ) {}

  findAll() { return []; }
}

Controller

import { Controller, Get, Param }
  from '@nestjs/common';

@Controller('users')
export class UsersController {
  constructor(
    private readonly svc: UsersService,
  ) {}

  @Get()
  findAll() { return this.svc.findAll(); }

  @Get(':id')
  one(@Param('id') id: string) { return id; }
}

Module that keeps a service private

@Module({
  controllers: [UsersController],
  providers:   [UsersService],
})
export class UsersModule {}

Module that shares it

@Module({
  controllers: [UsersController],
  providers:   [UsersService],
  exports:     [UsersService],   // lend
})
export class UsersModule {}

@Module({
  imports:   [UsersModule],      // borrow
  providers: [OrdersService],
})
export class OrdersModule {}

Injection scopes

ScopeInstancesUse when
DEFAULT One, shared app-wide, for the app's whole lifetime. Almost always. Requires stateless services. The default; do not declare it.
REQUEST One per incoming request, then garbage-collected. You genuinely need per-request state in the provider (e.g. multi-tenant context). Costs latency, and the scope bubbles up to every consumer.
TRANSIENT A fresh, dedicated instance per consumer. Rare. Typically loggers that must know who injected them.
 
@Injectable({ scope: Scope.REQUEST })
export class TenantContext {}

Docs → Injection Scopes. Default scope is a singleton, so never store per-request state on a provider field.

Error decoder

MessageIt meansFix
Nest can't resolve dependencies of the X (?). ... argument Y at index [0] is available in the Z context Nest built X, needed a Y, and could not find one registered in module Z. Add Y to Z's providers — or, if Y belongs to another module, export it there and import that module into Z.
... argument at index [0] is available in the ... context but the argument name shows as Object or undefined The type metadata was never emitted, usually a circular import between two files. Break the cycle, or use forwardRef(() => OtherModule) on both sides as a last resort.
Boots fine, but a shared cache or counter behaves oddly. The provider was listed in two modules' providers, so two instances exist. Declare it in exactly one module, export it, and import that module everywhere else.
One user sees another user's data, only under load. Per-request state stored on a singleton provider's field. Move the state out: pass it as a method argument, or persist it in the database or cache.

CLI, worth memorising

nest new <app>                # scaffold a project
nest g module users           # module (auto-imported into AppModule)
nest g controller users       # controller (auto-registered in UsersModule)
nest g service users          # provider  (auto-registered in UsersModule)
nest g resource users         # all of the above + CRUD + DTOs
npm run start:dev             # watch mode
Carry this forward

Singleton by default ⇒ services must be stateless ⇒ you can run N copies behind a load balancer. That chain is the reason this reference sheet sits at the front of a course about scale. See MISSION.md.
