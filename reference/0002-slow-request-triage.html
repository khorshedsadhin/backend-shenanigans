Reference 02 · Incident 01 এর সাথী

Slow Request Triage

API slow। কোথায় দেখবে, কোন order এ, আর কোন সংখ্যা কোন fix এর দিকে দেখায়।

মূল কথা

Request এর সময় = কাজ (CPU) + অপেক্ষা (waiting)। CPU graph শুধু কাজ দেখায়। অপেক্ষা CPU তে দেখা যায় না।

তিন ধাপ, এই order এ

ধাপকী করবেকী খুঁজছ
১ প্রতিটা core আলাদা দেখো। Windows: Task Manager → CPU → Logical processors। Linux: htop। একটা core ভরা, বাকি খালি → event loop এ ভারী কাজ। সব খালি → অপেক্ষা, ধাপ ২।
২ Slow endpoint এর প্রতিটা await এর আগে-পরে সময় log করো। মোট সময়ের বেশিরভাগ কোন একটা ধাপে যাচ্ছে।
৩ সবচেয়ে বড় সংখ্যাটা নিচের table এ মেলাও। ওটাই fix বলে দেয়। Guess করে fix বাছবে না।
 
const t = Date.now();
const rows = await this.db.query(...);
console.log('db query', Date.now() - t, 'ms');

লক্ষণ → কারণ → fix

যা দেখছসম্ভাব্য কারণFix এর দিকRoadmap
একটা core ১০০%, বাকি খালি। Slow endpoint চলার সময় সাধারণ endpoint ও আটকে যায়। Event loop এ CPU-heavy কাজ: বড় loop, বিশাল JSON, sync crypto। কাজটা request এর বাইরে সরাও (queue), বা আরো app instance। 13, 14
সব core কম। Timing log এ একটা query ই প্রায় পুরো সময় নেয়। Slow query, প্রায়ই পুরো table পড়ছে। EXPLAIN ANALYZE, তারপর index। 7
সব core কম। Query একা দ্রুত, কিন্তু load এ request সেকেন্ড নেয়। Connection pool saturated: সব connection busy, বাকিরা লাইনে। Pool size ঠিক করো, connection ধরে রাখার সময় কমাও, PgBouncer। 15
সব core কম। বাইরের API call এ সময় যাচ্ছে। Payment / SMS / অন্য service slow, timeout নেই। Timeout দাও। User এর অপেক্ষার দরকার না থাকলে queue তে পাঠাও। 13
সব core কম। একই row নিয়ে কাজ করা request গুলোই slow। Lock: একটা transaction আরেকটার জন্য অপেক্ষা করছে। Transaction ছোট রাখো, lock কম সময় ধরো। 6
ভুল fix এর ফাঁদ

আরো app instance সাহায্য করে শুধু যখন app এর CPU ভরা। Slow query হলে এটা একই database এ আরো চাপ দেয়। বড় server খালি CPU আরো বাড়ায়। আগে মাপো, পরে fix।
